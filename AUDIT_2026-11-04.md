## 2. Bugs confirmés

### B1 — PID file `llama-server.pid` périmé ⚠️ (le plus concret)
- Fichier : `~/.local/share/zer0gh0st/llama-server.pid` → contient **442035**.
- Réalité : ce PID **n'existe plus**. Le vrai `llama-server` tourne sous **PID 1305**
  (lancé le 2 nov., hors contrôle de Zer0).
- **Conséquence** : `stop_if_owned()` (`src/local.rs:272`) tentera un `kill -9`
  sur un PID mort → no-op silencieux, et Zer0 croit ne pas posséder le serveur.
  `restart_if_owned()` ne redémarrera jamais le serveur réel.
- **Fix** : au démarrage, vérifier que le PID existe **et** que le processus est
  bien un `llama-server` (via `/proc/<pid>/comm` sous Linux) ; sinon supprimer le
  fichier PID. Mieux : stocker aussi un token de démarrage pour détecter la
  réutilisation du PID par un autre processus.

### B2 — Base de connaissance : source indexée **en double**
La table `knowledge` contient **487 chunks** pour **un seul fichier** :

| source | chunks |
|---|---|
| `/home/omar0/ZER0v1/base_connaissance/public-apis.tsv` (absolu) | 249 |
| `base_connaissance/public-apis.tsv` (relatif) | 238 |

→ Le même contenu est indexé deux fois sous deux clés `source` différentes
(chemin absolu vs relatif). Ça fausse les scores FTS (doublons dans les
résultats) et double l'espace. Visible dans `knowledge.log` : chaque requête
retourne les deux variantes avec des scores quasi identiques (0.174 / 0.173).
- **Fix** : canonicaliser la `source` (chemin absolu normalisé) à l'indexation,
  ou dédupliquer au `INSERT`. Ajouter une commande de purge des doublons.

### B3 — `stop_if_owned` : `kill -9` d'emblée, pas de SIGTERM
`src/local.rs:281` envoie directement `kill -9` (SIGKILL) — pas de tentative
gracieuse (SIGTERM + délai). Le serveur n'a aucune chance de libérer la VRAM /
fermer proprement. `taskkill /F` côté Windows est l'équivalent forcé.
- **Fix** : SIGTERM, attendre ~2 s, SIGKILL seulement si encore vivant.

## 3. Manques & dette fonctionnelle

### M1 — Embeddings : table **vide** (0 ligne)
Le schéma `knowledge.db` prévoit `embeddings` + recherche hybride FTS5+cosinus
(`src/knowledge.rs`), mais **aucun embedding n'est calculé** sur cette machine
(pas d'embedder configuré). La recherche est donc **FTS5 pure** — le « hybride »
vanté est inactif en pratique.
- **Action** : soit documenter clairement « FTS seul par défaut », soit fournir
  un embedder local léger + commande `kb reindex --embed`.

### M2 — Doc obsolète : `tesseract-data-fra`
`docs/IMPROVEMENTS.md` liste « installer `tesseract-data-fra` » comme à faire.
**Déjà installé** (tesseract 5.5.3, langues `eng`+`fra`+`osd` présentes).
- **Action** : retirer cette ligne de la liste.

### M3 — `knowledge_delete` : pas d'outil exposé
L'API existe en interne (`knowledge_delete` par `source`) mais **l'outil agent
n'est pas câblé** (déjà noté dans IMPROVEMENTS.md). Un agent ne peut pas purger
une source obsolète — ce qui aurait été utile pour B2.

### M4 — Pas de framework de logs structurés
Aucune trace de `log`/`tracing`. Les erreurs partent en `eprintln!` éparpillés
(14 occurrences hors CLI : `audit.rs`, `telegram.rs`, `knowledge.rs`, `config.rs`…).
Pas de niveau, pas de fichier de log unifié, pas de rotation — alors qu'un
`audit.jsonl` existe déjà pour les actions.
- **Action** : introduire `tracing` + un subscriber fichier (réutiliser la
  rotation d'`audit.rs`), au moins pour les erreurs/warnings runtime.

### M5 — TTS / vision multimodale / tâches planifiées
Déjà documentés dans `docs/IMPROVEMENTS.md` comme **hors périmètre volontaire**
(TTS, vision réelle au-delà de l'OCR, exécution planifiée de tâches nécessitant
un démon). Pas des bugs — des choix assumés. RAS.

## 4. Robustesse du code (points à surveiller)

### R1 — ~141 `unwrap()` hors tests dans 27 fichiers
Concentration : `config.rs` (20), `audit.rs` (16), `zerochan.rs` (13),
`tasks.rs` (13), `commands.rs` (13), `vault.rs` (12), `text_editor.rs` (10),
`zer0-gw.rs` (10). Beaucoup sont sur des I/O fichier (`fs::write`, `read_to_string`)
ou du parsing — un disque plein, une permission ou un JSON corrompu = **panic**
au lieu d'une erreur propre.
- **Action** : pas tout convertir d'un coup, mais auditer en priorité les
  chemins chauds accessibles à l'agent (`text_editor.rs`, `vault.rs`,
  `zer0-gw.rs` — le gateway réseau ne doit jamais paniquer).

### R2 — Aucun MSRV déclaré
Pas de `rust-version` dans `Cargo.toml`. Le code utilise des APIs récentes
(`is_multiple_of`, `let-else`…) → échouera sur de vieux toolchains sans message
clair. **Action** : ajouter `rust-version = "1.8x"` + un job CI minimal.

### R3 — `cargo outdated` non disponible
Impossible de vérifier la fraîcheur des deps (pas installé, offline). Le
`Cargo.lock` est à jour vis-à-vis du build, mais aucune veille CVE visible
(pas de `cargo audit`/`dependabot` repéré dans `.github/workflows`).
- **Action** : ajouter `cargo audit` en CI (ou Dependabot/Renovate).

## 5. Sécurité

✅ **Points solides**
- Outils désarmés par défaut (`F4`/`--allow-exec`), avertissement clignotant.
- Coffre `/vault` chiffré (chacha20poly1305 + argon2), fichiers en `0600`
  (`vault.rs:172`, `config.rs:767`).
- Architecture **gateway** (`zer0-gw`) : l'agent ne voit jamais les clés API.
- Règle nftables d'egress (`deploy/20-zer0-egress.nft`) + services systemd dédiés.
- Aucun `unsafe`, pas de secret versionné (config en exemple, vraies clés en
  env/vault).

⚠️ **À renforcer**
- **R1** ci-dessus : un panic dans `zer0-gw` = gateway morte (DoS local).
- `kill -9` sur PID non vérifié (B1) : si le PID est réutilisé par un autre
  processus utilisateur, Zer0 pourrait tuer le mauvais processus.
- `memory.jsonl` est en `0600` ✅ mais `quota.json`/`knowledge.db` en `0644` —
  acceptable (pas de secrets), à confirmer si des données sensibles y transitent.
