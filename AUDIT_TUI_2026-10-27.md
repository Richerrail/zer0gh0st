## 1. Bugs confirmés

### 🔴 BUG 1 — `ctx 0%` : division entière qui écrase l'information

**Observé à l'écran**

```
ctx 0%/1.0M · 7033 tok
```

**Code** — `src/tui/mod.rs:4608-4614`

```rust
fn ctx_label(app: &App) -> String {
    let t = estimate_tokens(app);
    let pct = (t as u64 * 100 / app.context_window.max(1)).min(100);
    format!("{pct}%/{} ", ctx_window_label(app.context_window))
        .trim_end()
        .to_string()
}
```

**Preuve**

```
7033 tok / 1M = 0.7033 %  ->  affiché 0 %
```

**Impact** : tant que la conversation reste sous 10 000 tokens sur une fenêtre de 1 M, l'indicateur affiche `0 %`. Il ne bouge qu'à partir de 10 000 tokens. Sur un modèle 1 M, c'est **99 % de la plage utile** où l'indicateur ment. L'utilisateur ne peut pas anticiper la compaction automatique (~4000 tokens).

**Correctif proposé**

```rust
let pct = (t as f64 / app.context_window.max(1) as f64 * 100.0).min(100.0);
let label = if pct < 10.0 {
    format!("{pct:.1}")
} else {
    format!("{pct:.0}")
};
```

**Effort** : 5 min · **Fichier** : `src/tui/mod.rs`

### 🔴 BUG 2 — `O No project` est une chaîne codée en dur

**Observé à l'écran**

```
ctx 0%/1.0M · 7033 tok ······· O No project   think:off   role:off
Local /home/omar0   |   Projet /home/omar0/ZER0v1
```

Deux lignes qui se contredisent : « No project » puis « Projet /home/omar0/ZER0v1 ».

**Code** — `src/tui/mod.rs:4084`

```rust
Span::styled("O No project", Style::default().fg(Color::DarkGray)),
```

**Preuve**

```
rg -n "No project" src/   ->   src/tui/mod.rs:4084   (une seule occurrence)
```

C'est un **littéral**. Aucune condition, aucune variable, aucun appel à `load_project()`. Cette mention affichera « No project » **même avec un projet correctement chargé**.

**Correctif proposé** : appeler `config::load_project()` et n'afficher le nom du projet que si `.zer0/project.toml` existe ; sinon afficher `O No project` — mais pour de vrai.

**Effort** : 30 min · **Fichier** : `src/tui/mod.rs`

### 🔴 BUG 3 — Le chemin « Projet » est celui du binaire, pas du répertoire courant

**Observé à l'écran**

```
Local /home/omar0   |   Projet /home/omar0/ZER0v1
```

**Code** — `src/mods.rs:15-34`

```rust
pub fn project_root() -> PathBuf {
    if let Ok(root) = std::env::var("ZER0_ROOT") { ... }
    if let Ok(exe) = std::env::current_exe() {
        if let Some(root) = exe
            .parent()
            .and_then(|p| p.parent())
            .and_then(|p| p.parent())
        {
            return root.to_path_buf();
        }
    }
    std::env::current_dir().unwrap_or_else(|_| PathBuf::from("."))
}
```

**Preuve**

```
/home/omar0/ZER0v1/target/release/zer0  ->  /home/omar0/ZER0v1   ✅ (par chance)
/home/omar0/.cargo/bin/zer0             ->  /home/omar0          ❌
/usr/local/bin/zer0                     ->  /usr                 ❌
```

**Impact** : le « projet » affiché est **le dossier du binaire** (trois `parent()` depuis l'exécutable), pas le répertoire de travail. Lance `zer0` depuis `/tmp` : il affichera toujours `Projet /home/omar0/ZER0v1`. Le repli sur `current_dir()` n'est atteint que si `current_exe()` échoue — ce qui n'arrive jamais en pratique.

**Correctif proposé** : remonter depuis `current_dir()` à la recherche de `.zer0/project.toml` (ou `.git`), et ne retomber sur `current_exe()` qu'en dernier recours.

**Effort** : 30 min · **Fichier** : `src/mods.rs`

### 🟠 BUG 4 — Le markdown n'est pas rendu : les `###` s'affichent en clair

**Observé à l'écran**

```
### 🔴 4. Lecture de fichier non paginée
```

Les dièses sont visibles, le titre n'est ni gras ni coloré.

**Code** — `src/tui/mod.rs:4358-4425` (`push_block`)

Le rendu ne gère que deux choses :
- les blocs de code délimités par ` ``` ` (bascule `in_code`) ;
- `inline_spans` (`src/tui/mod.rs:4427`) qui ne traite que `` `code` `` et `**gras**`.

**Preuve**

```
rg -n 'starts_with("#")|heading' src/tui/mod.rs src/tui/banner.rs   ->   AUCUN résultat
```

**Impact** : titres `#`/`##`/`###`, listes `- `, citations `>`, tableaux, liens `[x](y)` : **rien n'est rendu**. Tout sort en texte brut. Les réponses structurées de l'agent deviennent des dumps difficiles à lire.

**Correctif proposé** : dans `push_block`, avant `inline_spans`, tester `seg.trim_start().starts_with('#')` → span en gras + couleur accent, en retirant les dièses. Idem pour `- ` (puce) et `> ` (barre verticale).

**Effort** : 1 h · **Fichier** : `src/tui/mod.rs`

### 🟠 BUG 5 — Le wrap coupe en plein mot

**Code** — `src/tui/mod.rs:4939-4959`

```rust
fn wrap_text(s: &str, width: usize) -> Vec<String> {
    let width = width.max(1);
    let mut out = Vec::new();
    for raw in s.split('\n') {
        if raw.is_empty() { out.push(String::new()); continue; }
        let mut cur = String::new();
        let mut count = 0;
        for ch in raw.chars() {
            if count >= width {
                out.push(std::mem::take(&mut cur));
                count = 0;
            }
            cur.push(ch);
            count += 1;
        }
        out.push(cur);
    }
    out
}
```

**Preuve** (largeur 40)

```
'Le manque est architectural, pas cosméti'
"que. Une mémoire incorrigible n'est pas "
'une mémoire.'
```

`cosméti|que` coupé en deux. Aucune recherche d'espace n'est faite : la coupe est purement positionnelle.

**Impact** : sur une largeur de chat étroite (fenêtre non maximisée, panneau latéral ouvert), chaque ligne longue est coupée au milieu d'un mot.

**Correctif proposé** : couper au dernier espace avant `width`, avec repli sur la coupe dure si un mot dépasse à lui seul la largeur.

**Effort** : 20 min · **Fichier** : `src/tui/mod.rs`

### 🟠 BUG 6 — Les emoji dépassent d'une colonne

**Code** — même `wrap_text` (`src/tui/mod.rs:4954`) : `count += 1` par `char`, alors qu'un emoji occupe **2 colonnes** en terminal.

**Preuve**

```
chars=40 cols=41 width=40  ->  OVERFLOW +1
```

```
'### 🔴 4. Lecture'      chars 16  cols 17
'### 🟠 5. Pas de'       chars 15  cols 16
'### 🟡 6. task_delete'  chars 20  cols 21
```

**Note** : `unicode-width` est **déjà présent dans `Cargo.lock`** (0.1.14 et 0.2.0, tiré par ratatui) mais **n'est pas utilisé** dans `wrap_text`.

**Impact** : toute ligne contenant 🔴🟠🟡 déborde d'une colonne et casse l'alignement du cadre. Combiné au BUG 4 (titres non rendus), les réponses à puces emoji sont les plus touchées.

**Correctif proposé**

```rust
use unicode_width::UnicodeWidthChar;
count += UnicodeWidthChar::width(ch).unwrap_or(1);
```

**Effort** : 10 min · **Fichier** : `src/tui/mod.rs` (+ `Cargo.toml` si la dépendance n'est pas déclarée en direct)

### 🔴 BUG 7 — Le footer n'indique jamais l'état des interrupteurs

**Observé à l'écran**

```
F3 Read&Write   F4 Code-exec
```

Gris uniforme, aucune indication d'état.

**Code** — `src/tui/mod.rs:4894-4910`

```rust
fn draw_footer(f: &mut Frame, area: Rect, app: &mut App) {
    let key = Style::default().fg(Color::Black).bg(Color::Cyan);
    let txt = Style::default().fg(Color::Gray);
    let spans = vec![
        ...
        Span::styled(" F3 ", key),
        Span::styled(" Read&Write  ", txt),
        Span::styled(" F4 ", key),
        Span::styled(" Code-exec  ", txt),
        ...
    ];
```

**Preuve**

```
rg -n "allow_exec|code_exec" src/tui/mod.rs
  -> 105, 106, 216, 231, 268, 321, 657, 829, 920, 922, 925, 996, 1952, 2203, ...
  -> AUCUNE occurrence entre 4894 et 4930 (corps de draw_footer)
```

`app.code_exec` et `app.read_write` existent (`src/tui/mod.rs:105-106`) mais **ne sont jamais lus** dans `draw_footer`. Le style `txt` est constant.

**Impact** : c'est le bug le plus **dangereux** de la liste. `code_exec` lance de vraies commandes shell avec les droits de l'utilisateur, sans bac à sable (`SAFETY.md`). L'écran ne dit pas si l'exécution est armée. L'utilisateur doit taper `/codeexec` pour le savoir — et le message de confirmation défile dans le chat.

**Correctif proposé**

```rust
let exec_style = if app.code_exec {
    Style::default().fg(Color::Black).bg(Color::Green)
} else {
    txt
};
let rw_style = if app.read_write {
    Style::default().fg(Color::Black).bg(Color::Yellow)
} else {
    txt
};
```

**Effort** : 5 min · **Fichier** : `src/tui/mod.rs`

**Preuve**

```

**Les 13 commandes absentes du panneau « Commandes »**

| Commande | Rôle |
|---|---|
| `/codeexec` | arme/désarme `code_exec` |
| `/readwrite` | arme/désarme l'écriture de fichiers |
| `/stream` | active/coupe le streaming |

**Impact** : ces commandes fonctionnent si on les tape, mais sont **indécouvrables**. Les deux plus critiques sont `/codeexec` et `/readwrite` : ce sont précisément celles qui arment les outils dangereux, et elles sont invisibles **alors que** le footer n'affiche pas leur état (BUG 7). **Correctif proposé** : ajouter les entrées manquantes à `TREE` dans `src/tui/menu.rs:63`, et faire échouer le test `flat_commands_is_non_empty_and_covers_model_provider_role` (`src/tui/menu.rs:322`) si une commande matchée dans `mod.rs` n'est pas dans `TREE`.

## 3. Ce qui manque — outils de l'agent

> **Correction importante.** Lors d'un tour précédent, j'ai affirmé que `code_exec` était absent de mon environnement. **C'était faux.** Vérification :
>
> ```
> code_exec OK
> Linux 7.2.8-9-omarchy x86_64
> /home/omar0
> 29912 /home/omar0/ZER0v1/README.md
> ```
>
> `code_exec` fonctionne, le réseau sort (`curl -> 200`), les processus en arrière-plan survivent (`nohup`). La leçon : **une capacité se prouve en l'appelant, pas en la déclarant.**

### Déjà couvert par le shell (donc PAS des manques)

`curl` `git` `python3` `rg` `fd` `jq` `sqlite3` `pdftotext` `tesseract` `convert`/`magick` `ffmpeg` `pw-record` `wl-copy` + venv Whisper (`~/.venvs/zer0-whisper`).

Avec ça, la majorité des « outils manquants » qu'on pourrait lister sont en réalité accessibles. Les vrais manques sont ci-dessous.

### 🔴 M1 — Aucune entrée visuelle

Je ne peux **pas recevoir d'image** : pas de `read_image`, pas de multimodal. Impossible de déboguer un rendu TUI depuis un screenshot sans passer par `tesseract` (qui lit du texte, pas une mise en page cassée).

**C'est le manque le plus coûteux pour un projet à interface TUI.**

### 🔴 M2 — Mémoire : écriture sans correction ni preuve

`memory_save` et `memory_search` existent, mais **ni `memory_update` ni `memory_delete`**. Une entrée fausse est définitive.

Le header de recherche l'avoue lui-même :

```
testables/probées/total : 20/0/21
```

**0 entrée prouvée sur 21.** On écrit dans une mémoire que rien ne valide jamais. C'est un défaut d'intégrité, pas de confort.

### 🟠 M3 — Base de connaissances en lecture seule

`knowledge_search` interroge `knowledge.db` (2,9 Mo ; tables `knowledge`, `embeddings`, `public_apis`, FTS5). Mais **aucun `knowledge_add`**.

Contournement possible en SQL brut via `sqlite3` — sauf que ça **court-circuite le pipeline d'embeddings** et corrompt l'index hybride. Le manque est architectural.

### 🟠 M4 — Lecture de fichier non paginée

`text_editor view` renvoie **tout** le fichier. Le README = 616 lignes / 30 Ko avalés d'un coup. Il manque un `read_file(path, offset, limit)`.

### 🟠 M5 — Pas de sous-agent à contexte isolé

`0box` fait débattre des perspectives mais **partage le contexte**. Pas d'équivalent `/ask` ou `/review` de Zer0 : un sous-agent avec son propre contexte, qui rend une synthèse. Tout ce qui est délégué pollue le fil principal.

### 🟡 M6 — `task_delete` absent

Création, `claim`, `done` — mais **pas de suppression**. Une tâche erronée reste dans `tasks.md` indéfiniment.

### 🟡 M7 — Pas de rendu JavaScript

`curl` ne rend pas le JS. Une doc sur un site SPA est inaccessible. Faible priorité.

### 🟡 M8 — Pas de sortie vocale

`pw-record` + Whisper = entrée audio OK. Aucun TTS : impossible de parler, alors que Zero-chan est un module du projet.

### 🟡 M9 — Pas de planification

`task_add` crée une tâche, mais rien ne la **déclenche** dans le temps. Pas de cron/schedule.
